# 大纲提炼与融合判断

## 先定档

同一件事做成工作流，分量可以差很多。先定档，别把三步的小事做成大工程。

档位判据（满足越多越该走完整档）：

| 信号 | 轻量 | 完整 |
| --- | --- | --- |
| 场景数 | 只有一种 | 两种以上，或会按情况分岔 |
| 阶段数 | ≤ 5 | 6 个以上 |
| 挂的技能 | 0–2 个 | 3 个以上 |
| 谁会读 | 只有用户自己、偶尔用 | 长期用、或要交接给别人 |
| 要不要留判据 | 不用，做法一看就懂 | 要，步骤有对错之分 |

档位决定要产出什么：

- 轻量：大纲 + 依赖登记 + 校验通过。不写取舍表、不写支线、不配脚本。
- 完整：大纲 + 支线结构 + 取舍表 + 每条步骤的命令与判据 +（值得时）脚本 + 校验通过。

拿不准按轻量走。轻量的工作流用着用着步骤在长，再从轻量升到完整档；反过来把大流程硬压成三五步，会让它在真用的时候卡住。

## 从素材里提炼大纲

先跟用户对话，再动笔。按 oil-plan 的做法：用两三个问题把这件事的起止、有几种情况、谁在用、什么时候算做完问清楚；用户答不上来，就先按轻量档写一版给他改，不要替他定死流程。大纲写成给人看的样子——他用日常话能读完、能指着某一阶段说「这里不对」。

按这个顺序找素材，前面的够用就不要往后翻：

1. 用户这次的描述。
2. 相关技能里已经写好的流程（技能的正文、它自己的 `references/`）。
3. 项目的 `AGENTS.md` 与已有的流程笔记。

提炼时只做一件事：把「这件事一共分几步」问清楚。每步写三样：

| 字段 | 要求 |
| --- | --- |
| 目标 | 这一步做完，什么东西变了 |
| 产出 | 具体产物：一段命令结果、一个文件、一次确认 |
| 涉及技能 | 有把握就写；没有写 `TODO`，等列完候选再回填 |

判断一个阶段是否该独立：它有独立的产出，并且做完能做一次判断（继续 / 重来 / 停下问用户）。只是同一步里的连续动作就合在一起。

- 阶段数量控制在 5–9 个。超过 9 个通常说明混进了两件事，拆成两个工作流。
- 大纲阶段不写命令、参数和判据。写了就会在没确认流程之前先锁死做法。
- 拿不准的地方宁可留 `TODO`，也不要编一个看起来完整的步骤。

## 筛候选技能

**动手前先核实这些事**，别照记忆写：

- 提到的技能真的装了（`wf.py scan` 里有），来源类型写对（上游仓库 / 本机目录 / 插件提供）。
- 路径真的存在，不是记忆里的旧路径。
- 要写进流程的命令先跑一次。跑不了或没跑过的，在 playbook 里标成「未验证」，不要写成确定结论。
- 涉及用户机器上的东西（仓库、目录、账号、已装工具）时先实测一遍。看着像重复的仓库可能是 worktree，看着装了工具可能没有。

先粗筛再复核：

```bash
py -3 <wf-maker>/scripts/wf.py scan --match "<关键词1> <关键词2>"
```

`--match` 按空格拆成多个关键词，命中任意一个就列出来。它只按名字和描述做字面匹配，会漏同义词，也会多带出只在描述里提过一句的技能。所以它只用来缩小范围，最终由你读完描述后决定。

还有一类技能 `scan` 根本列不出来：由插件提供、不在本机技能目录里的技能（例如文档、演示、表格这类宿主插件能力）。这类不在粗筛结果里，不等于没装；需要时直接问用户，或看宿主自己的插件清单。

复核时给每个候选标一档：

| 档位 | 判据 | 处理 |
| --- | --- | --- |
| 必用 | 大纲里有阶段离开它就做不成 | 进融合表，默认方式引用 |
| 可选 | 有它更顺，没有也能走 | 进融合表，标「可留可去」 |
| 无关 | 只是名字或触发词沾边 | 不列给用户 |

同一件事有两个技能都能做时，别都列上。按「谁更专门」选一个，另一个写在融合表的备注里，避免工作流里出现两条并行路径。

### 技能家族与替代关系

同一个能力常常有几个版本同时在库：免费版与高级版、通用版与专用版、旧版与新版。它们的名字和描述长得像，粗筛会一次全带出来。处理规则：

- 只登记这次真正走的那一个，一般选**更专门、更完整**的那个（例如同名的免费版与高级版，选高级版）。
- 被取代的那个不登记，写进 playbook 的备注，说明「什么情况下才换成它」，例如高级版缺失、或任务只需要免费版的能力。
- 描述里已经写了「有 X 时交给 X」的技能，按它自己的话办，不要自己另外挑。
- 两个都登记会让 `check` 两份漂移、`links` 两个引用，还让工作流在真用的时候出现两条路径，别这么干。

## 写触发描述:工作流怎么抢到该抢的活

工作流是「选路」技能,天然容易输给名字更具体的单个技能——用户说「做个页面」,宿主更容易直接挑 `oil-ui-pro`。避免办法不是把描述写长,而是写对:

- **触发词放最前面。** 开头就写「做设计时先走这条」「整理本地 git 时先用这条」,再列用户会说的原话。宿主是按描述匹配的,越早出现的词权重越高。
- **只留真会说的三五句。** 把「触发场景」压成 3–5 条口语,不要把所有变体都列上;堆得越长,越像泛泛而谈。
- **明确写「先走本技能」。** 一句话说明这是选路层:先由它决定调哪个具体技能。没有这句,宿主会认为它和具体技能是并列选项。
- **「不用于」只留最容易冲突的两三条。** 写多了等于自我介绍「别选我」。
- **别和具体技能抢同一句话。** 工作流描述写结果(「我要个能给人看的介绍页」),具体技能描述写做法(「生成 16:9 幻灯片」),两者不重叠才不会被互相挤掉。
- **用户手动点名时优先他点的那个。** 工作流是默认路径,不是强制路径。

改完描述要复验:`check` 会让引用它的工作流报「原技能已改动」,`link` 一次刷新基线;`validate` 确认描述没有和 README 撞重复。描述变动按 patch 版本升号,触发词或范围变了按 minor。

## 定融合方式

对每个「必用 / 可选」的候选，按下表定方式，然后让用户确认：

| 判断 | 方式 | 命令 |
| --- | --- | --- |
| 有上游仓库、会持续更新 | 引用 | `wf.py link <工作流> <技能> --uses "阶段 N：做什么"` |
| 本机自建、没有上游、以后换机器也要用 | 内置 | `wf.py bundle <工作流> <技能> --uses "阶段 N"` |
| 只需要它的一两条判断，工作流自己写得清 | 只写步骤 | `wf.py link <工作流> <技能> --mode inline --uses "阶段 N"` |
| 由插件提供、本机技能目录里没有 | 插件登记 | `wf.py link <工作流> <技能> --provider <插件名> --uses "阶段 N"` |

几条固定原则：

- **默认引用**。引用不产生副本，原技能更新后 `check` 会提醒，比快照省事。
- **内置只给没有上游来源的技能**。有仓库地址就写清单里的地址，别复制。
- **插件提供的技能只登记来源**。它没有本地路径，进不了哈希比对，`source.kind` 记成 `plugin`、带上插件名，环境清单里会写成「安装插件 X」。
- **凭据永远不进工作流**。需要密钥时用 `--credentials` 记「需要什么、放在哪」，值留在原处。
- **不内置另一个工作流**。工作流之间互相内置会让漂移说不清，改成引用。
- **不能删也不能改名**。技能名和上游仓库、目录名是绑定的，改名会断掉更新链路。要让它不打扰你，用隐藏（见 [maintenance.md](maintenance.md)）。

## 融合表长什么样

给用户的表只保留四列，按阶段排序：

| 阶段 | 技能 | 建议方式 | 理由 |
| --- | --- | --- | --- |
| 1 | ssh-remote | 内置 | 本机自建，没有上游仓库 |
| 2 | oil-plan | 引用 | 上游仓库会更新 |
| 3 | （无） | 只写步骤 | 只要两条判据，不值得引一个技能 |

用户勾完再动手。有争议的两项就只问这两项，不要把整张表重新念一遍。
