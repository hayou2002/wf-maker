# 维护流程

维护工作分五类：改工作流、看漂移、换方式、隐藏、删除。前两类随时可做，后三类要先说清影响、等用户确认。

## 改工作流

流程本身要动（加步骤、换技能、补判据）时，按这个顺序，不要直接上手改：

```bash
py -3 <wf-maker>/scripts/wf.py snapshot <工作流> --dry-run   # 先看快照计划
py -3 <wf-maker>/scripts/wf.py snapshot <工作流>             # 留一份旧版，放技能目录外的 workspace
```

- 快照放技能目录外，脚本拒绝覆盖已有快照；这样改坏了能对照，也能让另一个模型跑旧版做前后对比。
- 小改动可以直接改，但**每次动内容之前都值得留一份**——这个目录不在 Git 里，没有别的恢复途径。

改完之后：

```bash
py -3 <wf-maker>/scripts/wf.py bump <工作流> patch     # 预览版本号变化
py -3 <wf-maker>/scripts/wf.py bump <工作流> patch --write
py -3 <wf-maker>/scripts/wf.py check <工作流>
py -3 <wf-maker>/scripts/wf.py validate <工作流>
```

升版级别按改动性质选：补说明和修错用 `patch`，加按需步骤用 `minor`，改触发边界或删能力用 `major`。改完必须复验，只改完不验等于没改完。

## 看漂移

```bash
py -3 <wf-maker>/scripts/wf.py check            # 全部工作流
py -3 <wf-maker>/scripts/wf.py check wf-例子    # 单个
```

输出分三类，处理方式不同：

| 标记 | 含义 | 你该做什么 |
| --- | --- | --- |
| `[更新]` | 引用的技能内容变了 | 读一遍变更，问用户工作流里哪几条要跟着改 |
| `[注意]` | 内置副本和登记时不一致 | 确认是有意改的，还是有上游更新待同步 |
| `[问题]` | 登记的位置找不到了 | 阻断项。技能被删、被移走或根目录换了都会这样 |
| `[大纲]` | 还是 draft | 补内容、补清单，或跟用户确认先放着 |

漂移只报告，不自动改工作流。原技能改动常常和工作流无关，自动同步会把无关内容抄进工作流。

## 换融合方式

同一个技能可以换方式，命令会覆盖原登记：

```bash
py -3 <wf-maker>/scripts/wf.py link  <工作流> <技能>          # 改成引用
py -3 <wf-maker>/scripts/wf.py bundle <工作流> <技能>         # 改成内置，会写一份新副本
py -3 <wf-maker>/scripts/wf.py link  <工作流> <技能> --mode inline   # 改成不依赖
py -3 <wf-maker>/scripts/wf.py unbundle <工作流> <技能>       # 移除副本，改回不依赖
py -3 <wf-maker>/scripts/wf.py unlink <工作流> <技能>         # 引用改回不依赖
```

改完 `check` 会按新方式重新比对。内置改引用前先确认原技能还在，副本删掉就没了。

## 隐藏技能

目的：让某个技能不再出现在某个宿主的技能列表里，但文件和工作流引用都还在。

先查引用关系：

```bash
py -3 <wf-maker>/scripts/wf.py links <技能>
```

没有工作流用它，才是隐藏的候选。有工作流在用也可以隐藏，工作流会按登记路径继续读到它。

```bash
py -3 <wf-maker>/scripts/wf.py hide <技能> --agent <宿主>          # 只打印命令
py -3 <wf-maker>/scripts/wf.py hide <技能> --agent <宿主> --apply  # 确认后执行
py -3 <wf-maker>/scripts/wf.py unhide <技能> --agent <宿主> --apply
```

- 不带 `--apply` 只打印将要执行的命令和影响，把命令给用户看过再执行。
- 执行后核对：宿主的技能目录里那个名字是否消失，技能本身的文件是否还在。
- 隐藏只对技能管理器管着的技能有效。本机自建、不在管理器里的技能，本工具不动它；要收起它只能移动目录，那属于删除操作。
- 恢复用 `unhide`，把宿主加回原来的勾选列表。

## 删除与改名

- **删工作流**：整个 `wf-<名字>` 目录就是工作流。按四步走，不要一句话带过：
  1. 先列影响：目录在哪、里面有哪些文件、有哪些技能是只服务它的、环境清单和引用记录会一起消失。
  2. 先查引用：`links` 看这些技能还被谁用着，被别的流程用的不能一起删。
  3. 等用户明确同意，再动手删。
  4. 删完确认目录不在了，并告诉用户哪些登记记录同时消失。
- **删技能**：先 `links <技能>`。有工作流引用就不删；确实要删，先把工作流里的登记一并处理干净。
- **改名**：不给技能改名。上游来源、目录名和技能名是绑定的，改名会让更新和同步对不上。给工作流改名可以，注意避开别的技能已经占用的名字。

以上三类都属于不可逆或有外部影响的操作：先说清影响，等用户明确同意再动手。

## 环境清单

```bash
py -3 <wf-maker>/scripts/wf.py env <工作流>                # 重新生成 references/environment.md
py -3 <wf-maker>/scripts/wf.py env <工作流> --install-plan # 附带可执行的恢复命令
```

清单里记录：每个依赖的来源、安装方式、是不是内置、需要哪些凭据（只写位置）。换机器时按清单逐项装回来，再用 `check` 核对版本。

清单是生成物，不要手改。要改内容就改 `sources.json` 里的字段，或重跑 `link` / `bundle`，然后重新生成。

## 路径解析

技能被隐藏后，工作流仍然可用，因为依赖按「根目录代号 + 相对路径」登记：

```bash
py -3 <wf-maker>/scripts/wf.py show <工作流>
```

输出每个依赖解析后的实际路径、关系、是否被隐藏、有没有失联。技能根目录代号由 `wf.py roots` 列出。
