# 工作流 Skill 的结构与写作要求

生成出来的工作流和自己手写的技能一样，走同一套目录规范：`SKILL.md` 放顺序与判断，`references/` 放按需读的细节，`scripts/` 放确定、重复、可验证的步骤。

## 目录结构

```text
wf-<名字>/
  SKILL.md                     # 触发描述 + 阶段顺序 + 习惯与红线 + 停止点
  references/
    playbook.md                # 每个阶段的详细步骤，先大纲后填充
    habits.md                  # 个人注意事项与踩坑，可增长
    environment.md             # 环境清单，由 wf.py env 生成
    sops/                      # 可选：特定场景的细化 SOP
      index.md                 # 场景索引，没有 SOP 时不用建这个目录
      _template.md             # 新增 SOP 的骨架
      <场景>.md                # 一份 SOP 只写一个场景
  sources.json                 # 机器读的引用登记
  vendor/<技能名>/             # 内置副本，只有没上游来源的技能才放这里
```

## SKILL.md 要写什么

- **什么时候用**：哪些场景整段按这个工作流走；哪些细分任务直接找对应技能。写清边界，不要让工作流抢细分任务。
- **阶段表**：阶段、做什么、用哪个技能、产出。一眼能看完整条流程。
- **习惯与红线**：真正会改变结果的那几条，放到 `habits.md` 再从 SKILL.md 链接过去。
- **依赖与环境**：链接到 `environment.md`，不在这里重复安装步骤。
- **停止点**：哪一步必须等用户确认才能继续，写在该步旁边。

不写：具体命令与参数（进 `playbook.md`）、密钥值、单次任务的过程、修改记录。

## 写给不懂的人

工作流的读者常常不是专业开发者。借 oil-plan 的三条「不写」：

1. **不堆实现细节**：命令和参数放 `playbook.md`，`SKILL.md` 只说这一步要达成什么。
2. **不只甩文件名**：提到某个东西就顺手说它干什么，别让用户去猜。
3. **不用正确的废话**：「优化相关流程」「完善异常处理」这类不算内容，要写具体动作和能看见的结果。

外部可见变化优先于内部结构：写「推完能在仓库页面看到哪些提交」，不写「调整了推送逻辑」。

专业名词（worktree、tag、Release、PR、分支）第一次出现时，在 `playbook.md` 顶部配一节「名词速查」，一句话一个，用日常语言解释。用户看不懂的词，等于没写。

## 场景 SOP（可选）

通用 SOP 就是工作流主体：`SKILL.md` 加 `playbook.md`。`references/sops/` 只放特定场景的细化，不要重复主体流程。

- 只在用户点名场景时新增；没说就不加，避免让主流程分叉。
- 一份 SOP 只写一个场景，开头写清「所属主体」和「细化哪一步」。
- `index.md` 列出场景、细化范围和入口；用 `_template.md` 统一骨架。
- SOP 多了就在 `SKILL.md` 或 README 里提一句入口，方便按需打开。
- 单独技能也能用同样结构，放在该技能自己的 `references/sops/` 下。
- SOP 不进 `sources.json`，不是技能依赖，也不参与漂移比对。

## 信息架构

- 每类内容只放一处：触发信息在 frontmatter，顺序与判断在 `SKILL.md`，细节在 `references/`，确定的步骤在 `scripts/`。
- `SKILL.md` 控制在 150 行以内；超过 300 行先想清楚是不是混进了两件事。
- `references/` 单文件超过 200 行就加一节「目录」；只有某个阶段才用到的内容单独成文件，并在 `SKILL.md` 里写清读取时机。
- 不为形式完整建空目录：没有读取入口的资源，要么补入口要么删掉。
- 写给能力较弱的模型：一条指令一个动作，分支紧贴对应步骤，同一概念始终用同一个名字，不靠「照旧」「如上」指代。

## 版本号与升版

版本号写在 `SKILL.md` 的 `metadata.version`，格式 `主.次.补丁`，用双引号，写成多行映射（有些脚本按行读）。

- **补丁**：修错、补说明，不改触发方式和流程顺序。
- **次**：加可选步骤、加按需技能，老用法不受影响。
- **主**：删或改名能力、改触发边界、改依赖，老用法会失效。

改完工作流再升版，别每次都升；版本历史不写进 `SKILL.md` 正文。命令是 `wf.py bump <工作流> <级别>`，默认只预览，加 `--write` 才写。

## 触发描述怎么写

`description` 是唯一决定「什么时候加载」的地方，正文不重复它。常见四段：

1. 这个工作流做什么（用任务和产物说，不用模型或宿主名字代替）。
2. 哪些场景整段按它走——覆盖关键子步骤词，让它在这些场景下能接管。
3. 哪些相似任务不要触发，交给谁。
4. 一句分工：单个细分任务直接用对应技能，不必走完整流程。

工作流和它引用的技能在描述上会重叠，这是有意的：同时加载时以工作流的顺序为准，技能的内容只在对应步骤按需查。若某次运行发现细碎任务也被拉进大流程，优先收窄描述里的场景词，而不是往正文加规则。

## sources.json 字段

```json
{
  "workflow": "wf-例子",
  "title": "例子",
  "status": "draft",
  "created": "2026-01-01",
  "updated": "2026-01-01",
  "env_digest": "…",
  "sources": [
    {
      "name": "oil-plan",
      "mode": "reference",
      "source": { "kind": "github", "repo": "owner/repo", "subpath": "skills/oil-plan", "root": "library", "rel": "oil-plan" },
      "recorded": "2026-01-01",
      "digest": "sha256:…",
      "files": { "SKILL.md": "sha256:…" },
      "uses": "阶段 2：写方案",
      "credentials": "需要什么、放在哪"
    }
  ]
}
```

- `mode`：`reference` 引用、`bundle` 内置、`inline` 只写步骤（记一笔「这个技能不参与」）。由插件提供、本机技能目录里没有的技能也记成 `inline`，`source` 写成 `{"kind": "plugin", "provider": "插件名"}`，只进环境清单，不比对哈希。
- `source.root` + `source.rel`：技能根目录代号加相对路径。不写绝对路径，换机器时由脚本重新解析。
- `digest` 与 `files`：登记当时的内容哈希，`check` 靠它报漂移。`inline` 不记哈希。
- `bundle`：内置时额外记录 `dir`、`entry`、`excluded`、`rewrites`、`digest`。
- 文件多过 60 个时只存 `file_count`，不存逐文件哈希，输出仍然够用。

手工改 `sources.json` 后跑一次 `wf.py env` 刷新清单。

## 内置副本的规矩

- 入口文件 `SKILL.md` 改名为 `ENTRY.md`：技能发现会往子目录里找，原样放会被当成第二个同名技能。
- 凭据文件一律不复制：`.env` 系列（示例文件除外）、`credentials.json`、`secrets.json`、私钥与证书。留在环境清单的「凭据与配置」里说明去哪配。
- 副本里的本机绝对目录改写成 `~`，并记下改写次数。
- 副本是快照。原技能还在就两边都比哈希，原技能改了会提示「要不要刷新副本」。

## draft 与转正

- 未定稿的内容统一写成大写、单独出现的 `TODO`，`check` 就是按这个标记计数的。写完一段就把标记去掉。
- 新建默认 `draft`。`check` 会数 `playbook.md` 里的待办标记、看触发描述是否还是占位、环境清单是否生成过。
- 大纲态跑 `validate` 会报一条占位符警告，属于预期；转正前把它消掉。
- 转正条件：`playbook.md` 没有遗留 `TODO`，依赖都登记了，`check` 没有阻断项，`validate` 通过。
- 转正就是把 `sources.json` 的 `status` 改成 `active`，改完再跑一次 `check` 确认。
